# 面试亮点话术（可直接背）

> 用法：每个亮点按「场景 → 问题 → 方案 → 结果/数据 → 追问应对」组织，30–60 秒讲完。项目名统一叫 AISaaS 微服务平台（Spring Boot 3 + Spring Cloud + MyBatis-Plus + RocketMQ + Redis）。

---

## 亮点 1：服务间调用——强一致同步走 OpenFeign，异步走 MQ + 幂等

**场景**：对话主链路发起前要校验用户配额，这是强一致读；而真正的计费扣减是异步的。

**问题**：如果只用 RocketMQ 异步，配额校验拿不到实时结果，会超卖；如果强行同步调用又耦合、易雪崩。

**方案**：
- 同步部分用 **OpenFeign** `@FeignClient` 调 billing 的 `/internal/quota/check`（走 Nacos + LoadBalancer，无硬编码 IP）；`RequestInterceptor` 透传 `X-User-Id` / `X-Trace-Id`；`FallbackFactory` 选 **fail-open**（配额校验是保护性依赖，billing 抖动不该拖垮对话主链路）；超时收紧到 1s/2s。
- 异步部分继续走 **RocketMQ + 消费端幂等**。

**一句话总结**："强一致同步走 OpenFeign，可异步的计费走 MQ+幂等——这是标准答案。"

**追问**：为什么 fail-open 不 fail-closed？→ 核心写操作才 fail-closed；配额校验失败若 fail-closed 会让对话整体不可用，收益不抵风险。

## 亮点 2：MySQL 索引优化——会话列表分页 233 倍提速

**场景**：会话列表接口 `WHERE is_deleted=0 AND user_id=? ORDER BY is_pinned DESC, last_message_at DESC LIMIT 20` 是高频只读。

**问题**：原表建了 6 个单列索引（含低基数的 `is_deleted`/`status`）。`EXPLAIN ANALYZE` 显示优化器走 **index_merge 交集 + Using filesort**，扫描 2384 行，平均 ~500ms/查询，列表卡顿。

**方案**：删掉 6 个单列索引，改成 1 个**联合索引**
`(user_id, is_deleted, is_pinned DESC, last_message_at DESC)` —— 等值列在前、排序列在后且与 `ORDER BY` 方向一致（用降序索引避免反向扫描），让 `LIMIT` 直接下推到索引。

**结果**：计划变 `ref` 且**无 filesort**，扫描行数 2384 → 20，平均延迟 ~500ms → ~2ms（**约 233 倍**）；统计 COUNT 查询复用前导列无回归；索引数 6→1，写入放大更小。

**追问**：为什么低基数列不要单建索引？→ 选择性差，还会诱导 index_merge 反而更慢。索引不是越多越好。

## 亮点 3：Redis 缓存层——一套方案覆盖穿透/击穿/雪崩

**场景**：用户信息（每次鉴权都查）、配额记录（每次对话前 Feign 同步校验）、会话列表是三大热点只读。

**方案**：
- 用 Spring `@Cacheable`/`@CacheEvict`（common 里统一配好 `RedisCacheManager`），Cache-Aside：读缓存、写失效。
- **穿透**：用户缓存 `getById` **真实接入**布隆过滤器——`UserBloomFilter` 启动时全量载入 userId 构建 `RBloomFilter`（误判率 1%，预留 100w），回源前先查布隆，判定一定不存在直接返回拦截穿透（且不进缓存）；注册时增量 add；过滤器不可用则 fail-open 放行。quota/conversation 用 `unless="#result==null"` 不缓存空值。
- **击穿**：`@Cacheable(sync=true)` 对同 key 加锁，单线程回源（也可 `RedisUtils` 分布式锁做 singleflight）。
- **雪崩**：不同命名空间给不同 TTL（user 30min / quota 3s / conversation 30s），避免集体失效。
- **一致性**：quota 用短 TTL(3s)+扣减主动失效；user 在**全部写操作**（改资料/改密/改手机/改邮箱/上传头像/解绑/状态/删除）按 userId 失效，覆盖"改完资料读到旧数据"的盲区；conversation 写时整命名空间失效。

**结果**：鉴权与配额校验路径 DB/Feign 命中率大幅提升，DB 压力显著下降；并修复了 yml 中 `spring.redis` 应写 `spring.data.redis` 的配置坑。

**追问**：缓存和 DB 不一致怎么办？→ 读多写少用 Cache-Aside + 失效；强一致场景用短 TTL 兜底，或 Canal/binlog 订阅做准实时刷新（可展开）。

## 亮点 4（加分）：分布式事务与最终一致性

**场景**：计费扣减要保证"至少一次投递 + 不重复记账"。

**方案**：RocketMQ **半消息事务**（本地事务执行成功才提交半消息，失败回滚）+ 消费端 **Redis 幂等标记** + **DB 唯一键** 双保险 + **死信队列** + **定时对账补偿**（`UsageReconcileTask` 重放 pending）。

**结果**：五层防护，保证最终一致、不重复计费。

**可主动提的改进点（体现思考深度）**：当前事务状态存在内存 `ConcurrentHashMap`，重启或集群多实例会丢状态 → 应改为 Redis/DB 存储（源码注释里已标注）。

**追问**：为什么不用 2PC/TCC？→ 跨服务强一致成本高、锁资源；计费场景容忍最终一致，用事务消息 + 幂等 + 对账更合适。

## 通用追问准备

- 为什么选 RocketMQ 而不是 Kafka？→ 项目要事务消息 + 削峰填谷，RocketMQ 的事务消息/延迟消息更契合；Kafka 吞吐更高但事务支持弱。若 JD 要求 Kafka，可补一版 Kafka 收发 demo。
- 限流降级？→ 网关层已用 Sentinel 做了路由级 + 热点参数（userId）限流/熔断；业务服务也可加 `@SentinelResource`。
- 你遇到最难的问题？→ 任选上面一个，讲"现象→排查(EXPLAIN/压测)→根因→方案→数据验证"的闭环。
